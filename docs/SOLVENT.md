# [Solvent](https://github.com/PithomLabs/solvent) — Compliance as an Executable Authorization Layer

- https://github.com/PithomLabs/solvent

Compliance is not a sidebar to Solvent—it is the **second engine of the business**. Security asks whether a system can prevent or withstand bad outcomes. Compliance asks whether an organization can demonstrate that required controls were followed. Solvent makes the control itself executable: the same state that determines whether an agent may act can also preserve the evidence needed to explain what happened.

That duality is what can turn a security mechanism into infrastructure for regulated industries.

---

## 1. The Ledger Is the Audit Trail

Most compliance programs do not merely ask whether an AI system made the right decision. They ask whether the organization can demonstrate **what happened, who was responsible, what evidence was considered, which control applied, and what happened afterward**.

Solvent's ledger model is designed around that question rather than adding audit logging after the fact.

| Compliance Question | Solvent's Native Answer |
|---|---|
| *What evidence justified this action?* | `action_intent` → `belief` → `evidence` chain |
| *Who reviewed it?* | Debt retirement records the reviewer and justification |
| *Was the required evidence/control state satisfied before action?* | The authorization gate is tied to the required promoted/debt-free state |
| *What changed, and when?* | `belief_edge` records lineage, deduplication, and merge relationships |
| *Was the action ever walked back?* | `RetractCascade` preserves the original intent and records the resulting cancellation |

The important distinction is that **the enforcement state and the audit trail live in the same transactionally governed data model**. This is not a second logging system that merely hopes to match reality later.

That makes the architecture interesting to security teams and auditors for the same reason: the record of authorization is generated by the mechanism that enforced authorization.

The claim is not that Solvent automatically makes an organization SOC 2-, HIPAA-, FDA-, or EU-AI-Act-compliant. The claim is narrower—and more useful: **Solvent can make required controls observable, enforceable, and auditable instead of leaving them as documents and process promises.**

## 2. Regulatory Frameworks as Executable Control Templates

Every regulated industry has obligations that eventually become operational controls. Solvent's `debt` model provides a way to represent those controls as prerequisites for action.

The product opportunity is to ship **vetted control templates** that map regulatory obligations into executable authorization requirements.

| Industry | Regulatory / Governance Context | Example Solvent Control Obligations | Solvent Enforcement |
|---|---|---|---|
| **Healthcare / Medical Devices** | FDA QMSR / ISO 13485 environment | `needDesignReview`, `needValidationEvidence`, `needCAPAReview`, `needQualitySignoff` | A protected workflow can require the specified evidence/review state before promotion |
| **Finance** | MiFID II, FINRA/SEC and internal model/risk controls | `needRiskReview`, `needModelValidation`, `needConflictCheck`, `needComplianceSignoff` | Trading/advisory workflows can be gated on required controls |
| **Legal** | Professional-responsibility and firm governance controls | `needConflictCheck`, `needPrivilegeReview`, `needSupervisingAttorneySignoff` | A filing or client communication can remain blocked until required review is complete |
| **Software / Security** | SOC 2, ISO 27001, NIST-oriented control environments | `needThreatModelReview`, `needSecurityReview`, `needReleaseApproval` | Deployment or privileged changes can require evidence and explicit approval |
| **EU AI** | EU AI Act human-oversight, record-keeping and risk-management obligations | `needHumanOversight`, `needRiskReview`, `needMonitoringEvidence` | High-impact workflows can require the relevant review state before action |

These are **illustrative Solvent control mappings, not statements that a regulation prescribes these exact debt items**. The commercial opportunity is to turn the mapping work into a vetted configuration layer while keeping enforcement in the database.

That is the difference between selling another policy document and selling **compliance-as-code**.

A customer should not have to invent the control model from scratch. They should be able to adopt a vetted template, connect their evidence sources, define the authorized reviewers, and let Solvent enforce the resulting state transitions.

## 3. The Human-Oversight Boundary, Made Structural

For high-risk AI, the EU AI Act requires effective human oversight, including measures that allow people to monitor the system and, where appropriate, disregard, override, or reverse its outputs. Solvent is designed around the same architectural principle: **an agent may propose or investigate, but authorization is a separate state that must be earned.**

That matters because “human-in-the-loop” is often implemented as a notification, queue, or dashboard step. A notification can be ignored. A database invariant cannot.

- **Debt retirement carries an attestation.** A reviewer identity and justification become part of the record.
- **Authorization depends on control state.** The protected action cannot proceed unless the required prerequisites have been satisfied.
- **Retraction can propagate.** When a belief is invalidated, downstream intents can be cancelled rather than silently remaining authorized.

The technical implementation must be described precisely. Solvent should not be sold with a vague claim that “a CHECK constraint enforces compliance.” The defensible claim is:

> **The authorization path is transactionally constrained by the ledger state; the system cannot treat an unmet prerequisite as an authorized action.**

That is a better audit answer than “the agent was instructed to wait for approval.”

The broader idea is simple:

**Policy is descriptive. Solvent makes selected policy state executable.**

## 4. GhostJacking Shows Why This Boundary Matters

The strongest argument for Solvent is not a regulation. It is the failure mode that appears when an agent is trusted to interpret data and then act with legitimate permissions.

Tenet Security's 2026 GhostJacking research describes an agentic attack chain in which attacker-controlled information can enter through trusted telemetry or logs, influence an agent, and result in actions being taken through permissions the organization had already granted. The researchers reported 9-of-10 success against Claude Code in the tested configuration and demonstrated scenarios involving trusted platforms and consequential actions. The important lesson is independent of the exact exploit details: **an attacker does not always need to break the tool when they can influence what the agent believes and then let the agent's legitimate authority do the rest.** 

That is the problem Solvent attacks.

The critical boundary is not simply:

```text
untrusted input → trusted tool
```

It is:

```text
untrusted information
        ↓
agent forms a belief
        ↓
agent proposes an action
        ↓
authorization decision
        ↓
consequential action
```

Solvent is designed to put a hard gate between the last two steps.

The agent can be highly capable. The model can be wrong. The evidence can be stale. The security telemetry can be poisoned. **Capability does not automatically become authority.**

## 5. Compliance and Security Are Two Budgets for the Same Control Plane

| Dimension | Security / GhostJacking | Compliance / Governance |
|---|---|---|
| **Threat** | An attacker influences agent beliefs and exploits legitimate permissions | An organization cannot demonstrate that required controls were followed |
| **Failure mode** | Unauthorized or unsafe action | Action without required evidence, review, or traceability |
| **Solvent primitive** | Authorization gate tied to verified state | Same gate plus durable reviewer/control history |
| **Business value** | Reduce the probability and blast radius of consequential agent actions | Make controls enforceable and produce evidence for review |
| **Primary buyer** | CISO / security engineering | Compliance, risk, legal, quality, internal audit |
| **Underlying infrastructure** | Same ledger + evidence + authorization state | Same ledger + evidence + authorization state |

This is where the business case gets interesting.

**These are not two separate products. They are two budgets for the same control plane.**

A CISO can buy Solvent because an AI agent should not be able to turn poisoned information into an authorized action. A compliance or risk organization can buy the same infrastructure because required review and evidence should not depend on someone remembering to update a dashboard.

One deployment can therefore serve multiple control objectives, even though the exact regulatory mapping still has to be validated for each customer and use case.

That can make the product more resilient than a security-only positioning: security is the **why it matters now**; compliance is the **why the control becomes embedded in enterprise operations**.

## 6. The Trust Graph Can Extend Across Organizations

The next layer is supply-chain assurance.

A supplier, dependency maintainer, model provider, or service partner can publish a signed attestation that a particular belief or control state was satisfied at a particular time.

The pattern is:

1. An upstream organization establishes a belief such as *“CVE-2026-XXXX is remediated in release 2.3.4.”*
2. The required review/evidence debt is retired and the belief is promoted.
3. The organization publishes a signed attestation of that state.
4. A downstream organization consumes the attestation as evidence rather than treating the statement as unquestioned truth.
5. The downstream policy can require both the upstream attestation and an independent verification step.
6. Only when the downstream control state is satisfied can the action be authorized.

This is more interesting than a conventional compliance certificate because the evidence can become **machine-consumable input to another authorization decision**.

The commercial opportunity is a trust graph for agentic supply chains: evidence and attestations move between organizations, but each organization retains its own authorization boundary.

This pattern can support software-supply-chain assurance, provenance, traceability, and governance requirements. It should not be presented as though any regulator currently mandates Solvent's exact cryptographic attestation mechanism.

## 7. The Compliance API — A Roadmap Layer

Agents may speak MCP, while existing enterprise governance systems speak APIs and webhooks.

A future Solvent Compliance API could expose:

```text
GET  /v1/audit/belief/{id}
GET  /v1/audit/action/{id}
GET  /v1/compliance/report/{template}
POST /v1/compliance/webhook
```

Possible uses include:

- retrieving the evidence and authorization lineage for an action;
- generating customer-specific control evidence packages;
- notifying GRC systems when critical control states are retired, invalidated, or re-opened;
- feeding governance dashboards with machine-verifiable authorization history.

The integration opportunity is straightforward: Solvent becomes a control-data source for existing governance workflows rather than requiring customers to replace their entire GRC stack.

This is a **roadmap**, not a claim that these endpoints already exist.

## 8. Compliance as a Product Moat

The long-term product is not “AI compliance features.”

It is **a system in which selected non-compliant actions are structurally unable to proceed**.

The conventional model is:

```text
Write a policy.
↓
Tell the agent to follow it.
↓
Monitor logs.
↓
Assemble evidence when the auditor arrives.
```

Solvent's intended model is:

```text
Define the control.
↓
Attach evidence requirements.
↓
Require the appropriate review.
↓
Enforce authorization from database state.
↓
Generate the audit trail as part of the action.
```

That is a fundamental shift:

> **Compliance moves from documentation about the system to controls enforced by the system.**

It does not mean every regulation can be reduced to a database predicate. Nor does it eliminate the need for legal interpretation, organizational policy, or external audits. The opportunity is narrower and more practical: **where a requirement can be represented as an operational prerequisite, Solvent can make that prerequisite executable.**

That is the basis for a company.

## 10. The Business Thesis

The once-in-a-generation opportunity is not to build another agent.

The agent layer is becoming commoditized. Models change. Tool protocols change. Agent frameworks change. The capability to read, reason, and act is spreading rapidly.

What is not commoditized is the question enterprises eventually have to answer:

> **“Why was this action allowed?”**

For every consequential agent action, the durable system of record needs to answer:

- What did the system believe?
- What evidence supported that belief?
- Which controls were required?
- Who reviewed them?
- When did authorization become valid?
- What happened when the underlying belief changed?
- Can the organization prove all of that afterward?

That is the category I believe Solvent can own.

I am not betting that one model wins. I am betting that **organizations will eventually run many agents, and they will need one place where capability stops and authority begins.**

That is Solvent.

**The agent can believe. The organization decides when that belief is allowed to become action.**
